# fluidfoam benchmark

Reproducible benchmark comparing the reading of OpenFOAM output by fluidfoam
with other Python tools (foamlib, PyFoam, Ofpp) and with OpenFOAM's own
`reconstructPar` for decomposed cases. Besides timing, it checks that all
tools return the same values and counts the code a user has to write.

## Layout

```
bench/
    README.md                    # this file
    generate_bench_data.py       # synthetic datasets (no OpenFOAM needed)
    generate_real_decomp_case.py # REAL decomposed case (needs OpenFOAM)
    bench_compare.py             # driver: timing, memory, equality, report
    readers_fluidfoam.py         # code needed with fluidfoam
    readers_foamlib.py           # code needed with foamlib
    readers_other.py             # Ofpp, PyFoam
    check_foamlib_addressing.py  # does foamlib read the addressing files?
    reconstructpar.py            # reconstructPar + reading (needs OpenFOAM)
    data/                        # generated datasets (gitignored)
```

The tool-specific code is kept in separate `readers_*.py` modules on purpose:
each file contains exactly what a user of that tool has to write.

## Datasets

| Dataset | Generated by | Format | What it exercises |
|---|---|---|---|
| `case_ascii` | `generate_bench_data.py` | ASCII | text parsing |
| `case_binary` | `generate_bench_data.py` | binary, LSB | binary decoding |
| `case_binary_gz` | `generate_bench_data.py` | binary + gzip | compressed reading |
| `case_decomp` | `generate_bench_data.py` | decomposed, N procs | reconstruction, **contiguous** decomposition |
| `case_decomp_real` | `generate_real_decomp_case.py` | binary, 64 procs | reconstruction, **non-contiguous** decomposition, `reconstructPar` |

All cases contain the same kind of deterministic non-uniform scalar field
`alpha` (seeded RNG, reproducible bit-for-bit).

**Why two decomposed cases?** The synthetic `case_decomp` only contains the
addressing files and splits the cells into contiguous chunks. It is cheap
and needs no OpenFOAM, but it hides the reordering work: concatenating the
per-processor arrays gives the right answer only because the decomposition
is contiguous, and `reconstructPar` cannot process it (no real `polyMesh`).
`case_decomp_real` is built with `blockMesh` and `decomposePar` (method
`simple`, 4x4x4 blocks): `cellProcAddressing` is then not contiguous, as in
a real run, and the cell reordering has to be done correctly. It also
provides `reference_alpha.npy`, the field in global cell order, which is a
ground truth independent of any reader.

## What the user has to write

With fluidfoam, a decomposed case is read with one call, exactly like a
reconstructed one:

```python
def read_decomposed(case, time, name):
    return fluidfoam.readscalar(case, time, name)
```

With foamlib, which reads one file at a time, the user has to find the
processor directories, read each file and put the cells back in global order
using `cellProcAddressing` (read with foamlib itself, `FoamFile(path)[None]`):

```python
def _processor_dirs(case):
    return sorted(
        (d for d in os.listdir(case) if d.startswith("processor")),
        key=lambda d: int(d[len("processor"):] or 0),
    )

def _read_processor_field(case, proc, time, name):
    path = os.path.join(case, proc, time, name)
    if not os.path.exists(path) and os.path.exists(path + ".gz"):
        path += ".gz"
    f = FoamFieldFile(path)
    arr = np.asarray(f.internal_field)
    del f
    return arr

def _read_addressing_native(path):
    if not os.path.exists(path) and os.path.exists(path + ".gz"):
        path += ".gz"
    with FoamFile(path) as f:
        return np.asarray(f[None])

def _assemble(case, time, name, read_addressing):
    parts, addrs = [], []
    for p in _processor_dirs(case):
        parts.append(_read_processor_field(case, p, time, name))
        addrs.append(
            read_addressing(
                os.path.join(case, p, "constant", "polyMesh",
                             "cellProcAddressing")
            )
        )
    out = np.empty(sum(len(a) for a in addrs), dtype=parts[0].dtype)
    for part, addr in zip(parts, addrs):
        out[addr] = part
    return out

def read_foamlib_addressed(case, time, name):
    return _assemble(case, time, name, _read_addressing_native)
```

`foamlib(addr+parser)` is a cross-check variant that reads the addressing
files with our own parser instead of foamlib (its parser is not counted as
user code, in favour of foamlib). It is the fallback if the installed
foamlib version cannot read these files: run
`python bench/check_foamlib_addressing.py --case bench/data/case_decomp_real`
to find out (see "Known limitations").

`bench_compare.py` prints the number of lines for each tool. A third
possibility is OpenFOAM's `reconstructPar -fields '(alpha)' -time ...`
followed by a read of the reconstructed field: no Python code to write, but
it needs an OpenFOAM installation, writes the field to disk and is timed
below.

A naive `np.concatenate` of the per-processor arrays is also benchmarked as
`foamlib(concat)`. It is valid only for contiguous decompositions: the
equality check shows that it fails on `case_decomp_real`.

## Metrics

- end-to-end wall time (median over N runs); warm cache by default,
  client-cold cache with `--cold`
- peak memory (`tracemalloc`; Python allocations only, so for
  `reconstructPar` it covers the read of the reconstructed field, not the
  OpenFOAM process)
- value equality across tools (`np.allclose`) and against the ground truth
  when `reference_<field>.npy` is present, one line per tool
- user code needed (lines of Python)

`--cold` evicts the page cache of every file of the case before each timed
run (`posix_fadvise(DONTNEED)`, no root needed). It acts on the client
only: the cache of an NFS server cannot be flushed from user space, so
"cold" means "client-cold".

## Usage

Generate the datasets (a few seconds for 10k cells, ~20 s for 1e6):

```bash
python bench/generate_bench_data.py --outdir bench/data --ncells 1000000 --nproc 64
```

Run the comparison (each tool is used only if installed):

```bash
pip install fluidfoam foamlib Ofpp PyFoam   # subset is fine

# reconstructed cases
python bench/bench_compare.py --case bench/data/case_ascii     --time 0 --runs 10
python bench/bench_compare.py --case bench/data/case_binary    --time 0 --runs 10
python bench/bench_compare.py --case bench/data/case_binary_gz --time 0 --runs 10

# synthetic decomposed case (contiguous: foamlib(concat) is valid here)
python bench/bench_compare.py --case bench/data/case_decomp --time 0 --decomposed --runs 10
```

Real decomposed case and `reconstructPar` (OpenFOAM environment sourced):

```bash
python bench/generate_real_decomp_case.py --outdir bench/data/case_decomp_real \
    --n 100 --grid 4 4 4            # add --format ascii for ASCII data

python bench/check_foamlib_addressing.py --case bench/data/case_decomp_real

python bench/bench_compare.py --case bench/data/case_decomp_real --time 0 \
    --decomposed --with-reconstructpar --runs 10           # warm cache
python bench/bench_compare.py --case bench/data/case_decomp_real --time 0 \
    --decomposed --with-reconstructpar --cold --runs 5     # client-cold
```

`--with-reconstructpar` works on a copy of the case (made next to the
original, or in `--workdir`) because `reconstructPar` writes the
reconstructed field into the case; the copy is removed at the end. At time 0
the option `-withZero` is added, since `reconstructPar` skips time 0
otherwise.

Optional threaded reading for fluidfoam:

```bash
FLUIDFOAM_NTHREADS=8 python bench/bench_compare.py --case bench/data/case_decomp --time 0 --decomposed
```

## Known limitations

- PyFoam does not parse binary lists into arrays: on binary cases the
  reader raises an error instead of reporting a time that would not
  correspond to reading the field. Use the ASCII case for PyFoam.
- foamlib reads files without keyword (such as `cellProcAddressing`) with
  `FoamFile(path)[None]`. Its binary list parser was fixed in March 2026
  (gerlero/foamlib pull request 762, sporadic parsing errors with binary
  lists) and, according to that description, guesses the data type among
  int32, float64 and float64x3, so binary files with 64-bit labels may not
  be supported. Use a recent foamlib, run `check_foamlib_addressing.py` and
  report the foamlib version with the results.
- The reading of the reconstructed field assumes that fluidfoam reads the
  time directory of the case itself when it exists next to the
  `processor*` directories.
- Timings depend on the machine and on the file system (local disk, NFS,
  Lustre). Report them with the hardware, the file system and the versions
  of all tools (`python -c "import fluidfoam, foamlib; print(fluidfoam.__version__, foamlib.__version__)"`,
  `echo $WM_PROJECT_VERSION`).

## Datasets are gitignored

`bench/data/` is excluded from the repository because it is large and
fully regenerable. Continuous integration regenerates a small version
(10k cells) and checks that all datasets are written and read back
identically (see `.github/workflows/bench.yml`). The real decomposed case
needs OpenFOAM and is not part of the CI.

## Notes for the JOSS paper

The numbers quoted in the paper come from:

```bash
python bench/generate_bench_data.py --ncells 1000000 --nproc 64
python bench/generate_real_decomp_case.py --outdir bench/data/case_decomp_real
python bench/bench_compare.py --case bench/data/case_binary --time 0 --runs 10
python bench/bench_compare.py --case bench/data/case_decomp_real --time 0 \
    --decomposed --with-reconstructpar --cold --runs 5
```

on the machine specified in the paper. Raw outputs are archived with the
release. fluidfoam is not necessarily the fastest reader of a single file;
the benchmark documents its cost and shows what it saves the user: no
per-processor assembly code (see "What the user has to write"), a
reconstruction validated against a ground truth, and no OpenFOAM
installation or intermediate files.
